# 实现变更与配套契约同步契约

Status: implemented
Contract-ID: development-workflow/contract-sync
Parent: specs/implemented/development-workflow.spec.md

## 范围与非目标

约束本仓库实现、配置、消息定义、接口、目录与契约改动的配套契约核对流程。
本叶拥有关联数据和同步记录格式，不复制业务要求，不证明业务处置充分或实现正确。
只读检查不得触发业务测试、构建、部署或读取主机凭据。

## 术语与身份

- **R1 任务范围**：开始修改前明确的仓库相对路径集合；目录范围包含其全部后代。
- **R2 基线**：任务范围内文件指纹及当时契约关联图。已有未提交内容是起点，
  只有基线之后的文件内容或存在性变化才计入本轮；同范围并发变化不得被自动忽略。
- **R3 候选契约**：由实际差异、路径绑定、反向依赖和父根登记推导的待核对集合。
  候选意味着必须处置，不意味着必须改动业务条款。
- **R4 身份**：关联与处置使用 Contract-ID，不以文件行号、历史决定或任务序号替代。

## 输入、输出与配置

### 1. 叶契约关联数据

每份 implemented、proposed 叶在“归属与依赖”下声明恰好一个 contract-links JSON 块。
implementation 是仓库相对路径模式数组，depends_on 是实际存在的生效或提案契约 ID 数组。
数组不得有重复项；不填虚构路径或空占位。纯规范叶也应绑定其约束的治理文件。
depends_on 必须包含其约束边界所属的父根 ID；其它引用按实际消费要求或文档依赖声明。

模式按 POSIX 路径分段：`*`、`?` 只匹配本段，独立 `**` 匹配零个或多个目录段。
禁止绝对路径、上级目录、空段和反斜线。模式用于声明约束范围，不要求未来路径已经创建。
一个实现文件可受多个不同方面的契约约束，不要求路径绑定互斥。

### 2. 任务基线

捕获入口：`python3 specs/tools/station-host-spec-lint.py --capture-baseline <忽略区文件> --scope <任务路径>`。
多个 scope 重复传入；必须在开始修改前捕获，不允许用修改后的状态冒充起点。
目标必须位于本仓库的 `.artifacts/spec-sync/` Git 忽略区、以 `.json` 结尾且尚不存在；
不覆盖已有基线，不写入版本控制，不读取其它主机本地文件充当基线。
基线保存 schema=1、仓库位置摘要 repo_id、当前 head、scopes、files 和 contracts。
files 为路径到 SHA-256 或 null 的映射，null 表示该路径不存在；不保存源码内容。
contracts 保存每个有效契约的 path、parent ID、implementation 和 depends_on。

### 3. 同步记录

方案 §5 包含恰好一个 contract-sync JSON 块，键集为 baseline、baseline_sha256、reviews。
baseline 是忽略区基线文件的相对路径；baseline_sha256 固定其原始字节摘要，防止基线被覆盖。
reviews 数组每项包含且仅包含 id、clauses、status、reason、evidence。

- id：候选 Contract-ID；不得重复，不得用未知 ID 凑记录。
- clauses：非空字符串数组，指向核对的章节或条款；例如“归属与依赖/变更关联”或“§3”。
  可使用原有稳定条款编号；当前有效契约中定位必须存在。整体删除或归档而无当前有效文件时，
  分别使用“整体删除”或“整体归档”，并提供删除前基线或归档文件证据。
- status：updated、unchanged 或 pending；交付检查不允许 pending。
- reason：具体中文说明，至少八个字符；解释修改影响及处置，不得只写“无影响”。
- evidence：非空仓库相对路径数组，指向本轮文件、契约或调查记录；删除项可引用基线中存在的路径。

updated 表示对应契约文件相对基线确有变化；unchanged 表示核对后无需修改，不能伪造文件更新。
记录格式和文件差异可自动判断，理由与条款是否充分仍由执行者审阅，不由门禁推断。

## 行为规则

- **R5 自动触发**：任何实现、配置、消息、接口或目录改动必须建立基线和契约处置记录，
  不因使用者没提到 specs 而跳过。仅修契约同样执行关联核对。
- **R6 差异完整**：对比基线与当前工作区，包含 tracked、untracked、新增、删除、重命名两端。
  不以全部未提交文件直接冒充本轮修改，也不只检查暂存区。
- **R7 双版关联**：使用基线和当前关联图的并集识别旧路径、被删除契约及新绑定；
  实现路径匹配及被改契约自身先入候选，再传递核对反向依赖，最后加入父根。
  最后因登记加入的父根不再展开同级叶；根本身发生改动时，其显式依赖方仍须核对。
- **R8 无静默遗漏**：每个候选必须有处置记录；没有任何绑定的改动必须补充归属，不能忽略。
  路径绑定只是发现机制，执行者发现额外消费者时必须补充依赖与同步记录。
- **R9 同轮同步**：确需修订的配套契约必须与实现作为同一任务交付；无需修改的逐项说明理由。
  提交仍遵循各 owner 仓库与子树纪律，本叶不授权混合提交或推送。
- **R10 对外边界**：发现受影响的外部 owner 时，在相关契约处置理由和方案中登记依赖、
  证据及剩余工作；未处理的实际影响保持 pending，不用本仓库结构通过宣称跨仓库同步完成。

## 失败、取消与资源生命周期

- **R11 拒绝条件**：缺失或损坏基线、摘要不符、仓库不符、未映射改动、漏项、重复处置、
  pending、无理由或证据、updated 却无契约差异均必须返回非零。
- **R12 任务恢复**：中断后沿用同一基线，新增范围必须先捕获相应起点并明确拆分任务，
  不重置已有范围以抹除差异。基线在检查完成前不得删除；保留或清理由操作者显式执行。
- **R13 许可**：基线捕获仅写明确的主机忽略区文件；检查模式只读，不调用业务程序。
  未获检查许可时登记待检查，不宣称同步完成；测试许可仍以 AGENTS 为准。

## 归属与依赖

本叶唯一拥有实现变更的契约关联、候选发现与处置记录；README 负责模板与生命周期规则，
AGENTS 负责强制读取入口，方案负责本轮事实和证据，不建立另一份契约权威。

## 条款检查判据

- **SYNC1**：关联块完整且 ID 有效，模式符合 §1。
- **SYNC2**：捕获与读取基线符合 §2、R2、R6，能识别新增和删除。
- **SYNC3**：候选按 R7 推导，记录覆盖全部候选；未绑定改动按 R8 拒绝。
- **SYNC4**：处置字段、理由、证据与 updated 差异符合 §3、R11。
- **SYNC5**：`--list-impacts <方案>` 仅输出候选，不表示同步通过；
  `--sync-plan <方案>` 只有结构与全部处置通过才返回 0。
- **SYNC6**：检查结果明确不证明业务内容、运行实现或外部仓库通过；不安装预提交钩子。
