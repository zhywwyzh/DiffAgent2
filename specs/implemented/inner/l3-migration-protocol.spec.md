# 旧库到新库迁移规程

Status: implemented

Contract-ID: l3-dispatcher/migration-protocol
Parent: specs/implemented/l3-dispatcher.spec.md

> 适用于 l3 一切从旧库（DiffAgent2 旧版）向新库（DiffAgent2 新版）的迁移
> 与重构活动。
> 本规程只规定**流程与判据**，不规定某一轮改什么文件——后者归
> `doc/l3-dispatcher-planner/iteration/` 下的方案所有。

## 1. 总原则

> 违反任一条即缺陷。

- **契约先行**：任何迁移轮次开始前，其目标形态必须已在 `specs/` 中有契约
  （`proposed` 及以上）。没有契约的迁移不得开始。
- **重新评估执行逻辑**：迁移 DiffAgent2 旧版设计时，必须结合 DiffAgent2 新版的
  任务流程、能力归属与通信机制，评估是否应重新设计执行逻辑。旧版的调用顺序、
  话题划分和消息类型不默认成为新版约束；保留或重设计均须记录依据。
- **无调用方不迁**：旧库中无任何调用方的符号、文件与包，一律不迁移。
- **不留半成品**：被替代的旧功能直接删除，不得保留为转接口，不得仅注释掉。
- **不留桩**：不得为"以后可能用"而保留空实现、注释桩或占位分支。
- **不新增转接层**：新旧接口不统一时，重新设计接口，不得新设一层适配器桥接。

## 2. 归属裁决

> 每个待迁移的旧库单元按下列顺序裁决；顺序在上者优先，命中即止。

1. 属于分发骨架（状态机、任务队列、相位上报、全局停止）→ core，受
   `l3-core-boundary` 约束；
2. 只在某一任务流程中被调用 → 对应技能，受 `l3-skill-contract` 约束；
3. 跨多个任务共享的感知、几何或外部推理能力 → 共享服务；
4. 属于下行执行且被多个任务共享 → 执行缝，受 `l3-execution-seam` 约束；
5. 属于运动规划 → 不属本契约范围，保持独立；
6. 无任何调用方，或为调试残留 → **不迁移**；
7. 对应任务上游尚未实现 → 仅在 `doc/l3-dispatcher-planner/rest/` 台账中
   登记能力身份、依赖、触发条件与验收；**不创建空技能类、占位注册或旧实现**。
   文档登记不构成生产能力，不豁免“不留桩”规则。

- 裁决结果必须记录在该轮方案内，逐项可追溯。
- 裁决不明时补契约，不得凭当轮执行者的判断默认放行。

### 2.1 执行逻辑与交互机制评估

完成归属裁决后，迁移方案必须说明以下内容：

1. **保留的业务语义**：明确任务目标、完成判据、多行为反馈的汇合条件、失败处理、
   取消优先级及任务资源释放边界；区分这些要求与旧版的具体实现手段。
2. **旧链路的问题与新链路的选择**：梳理指令发出、接收确认、进度反馈、结果返回、
   取消和超时处理的责任方，评估重复状态、跨话题关联及等待链是否可以简化。
   按交互性质选择话题、服务或 Action 等机制，不要求一律更换通信方式。
3. **重设计的范围与依据**：记录旧执行流程、目标执行流程，以及保留、重写、删除的
   部分和理由。选择应减少重复协议与分散的状态管理，同时保留业务与安全语义；
   不得仅为沿用旧版接口而复制原有交互链。
4. **调用方与迁移闭包**：明确受影响的生产者、消费者、契约和配置如何同步修改。
   涉及待迁依赖时同步更新 `doc/l3-dispatcher-planner/rest/` 台账；被替代的实现
   直接删除，不以新增转接器或保留旧入口完成迁移。

例如，长时间运行且需要进度、结果与取消的规划或导航任务，应评估使用 ROS Action
统一目标生命周期，替代旧版通过多个话题和消息类型分别传递指令、确认、进度与完成
状态的设计。连续建图、定位等数据流仍按其自身通信需求设计；跨行为的业务汇合条件
仍由对应流程负责，不能仅凭单个 Action 结束判定整个任务完成。

采用 Action 时，取消请求被接受与设备已经停止必须有明确区分。取消应保留强制停止、
紧急悬停和释放当前任务资源的要求，不得清空地图、终止常驻建图或释放其他任务及共享
服务的资源；具体行为以执行缝及对应技能契约为准。

## 3. 准入条件

> 每一轮迁移开始前必须全部满足。

- 目标契约已就位，且本轮涉及的禁令与门禁条目已确定；
- 待迁移清单已完成 §2 归属裁决；
- 已完成 §2.1 执行逻辑与交互机制评估，方案已记录保留或重设计的依据及调用方迁移安排；
- 无调用方检测已执行，结果已记录；
- 若本轮会变更对外行为契约（主题名、服务名、action 名、消息字段名、
  结构化日志事件名），已明确登记为有意变更并给出兼容处置。

## 4. 禁止事项

- **禁止转接器**：不得为桥接新旧接口新增任何层。
- **禁止遗留垫片**：不得为兼容旧调用方保留旧入口。
- **禁止注释桩**：被删代码直接删除，不留注释块、空方法或 docstring 桩。
- **禁止双写**：同一份数据不得同时经端口与共享内存两条路写入。
- **禁止假成功**：任何能力缺失、未注册、未就绪的情形，必须上报失败并停
  在安全态，不得静默返回成功。
- **禁止项目本地契约**：契约只写在 `specs/` 下，不得散落在代码仓或 `doc/`
  里形成第二权威。
- **禁止引入中间表示**：不得引入任务编号或等价的枚举映射作为任务识别与
  能力归属之间的中间层；直接依据 rpc-json 的解析结果分发。旧库中一切与
  任务编号相关的常量表、映射结构、解析与校验逻辑，一律不迁移。

## 5. 契约与实现的漂移处理

> 发现代码与契约冲突时的处置顺序。

1. 判定哪一方过时：契约描述的是目标形态，代码可能是未迁移的过渡态；
2. 若契约正确、实现未跟上 → 修实现；待办登记在该轮方案或 issue 中，
   **不进契约**，不得改契约迁就现状；
3. 若契约本身已被后续决策推翻 → **先改契约**（同一改动内），再动实现；
4. 禁止"先迁移、后对齐契约"——漂移会在每一轮累积。

## 6. 验收

> 每轮必须完成与轮次性质匹配的验收。
>
> **统一声明**：除非使用者明确许可，否则跳过验收测试工作（`AGENTS.md` 硬性约束 §9）。

- **静态验收（每轮必做）**：语法检查通过；引用闭包无未解析符号；删除项
  零残留；纯删除轮次须证明除显式允许的片段外无任何新增行。
- **运行时验收（可达端到端时必做）**：若本轮结束时链路可运行，必须做
  端到端验证；若不可运行，必须在方案中显式登记"本轮结束时不可运行"及
  预期恢复的轮次，并说明回归手段。
- **行为契约核对**：主题名、服务名、action 名、消息字段名、结构化日志
  事件名，除已登记的有意变更外保持不变。

## 7. 交付物与归档

- 每轮产出一份方案，落 `doc/l3-dispatcher-planner/iteration/`，格式遵循
  该目录模板；该方案是**过程材料，非权威**；
- 方案执行完毕（该轮状态置 `done`）时，在**同一改动内**把其"为什么这样变"的
  部分归档为决策记录，落 `specs/implemented/architecture/yyyy-mm-dd-<topic>.md`
  （工作流/工具类决策落 `specs/implemented/process/`；布局见 `specs/README.md`
  §生命周期布局）。决策记录冻结、不再维护，方案的其余部分不迁移；
- 工作区不留中间产物；临时快照放主机本地，不入库；
- 提交前执行隐私检索，个人凭据零命中。

## 8. 门禁

| 门禁 | 检查 |
|------|------|
| G18 | 本轮涉及的目标契约存在于 `specs/` 且状态为 `proposed` 及以上（§3） |
| G19 | 无调用方检测零遗漏：迁入的每个符号都有活调用方（§1） |
| G20 | 被替代功能的旧实现已删除，无转接口、无注释桩（§1、§4） |
| G21 | 行为契约字符串级 diff 与登记的有意变更一致（§3、§6） |
| G22 | 新增代码不出现"未注册即静默成功"的路径（§4） |
| G23 | 迁移后的代码零引入任务编号标识符；旧库的编号常量表、映射结构与解析校验逻辑未出现在新库（§4） |
