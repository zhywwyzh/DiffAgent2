# specs — 统一 spec 注册表

> 本文件是契约分类、编写、生命周期与变更规则的唯一入口。系统事实与详细要求
> 归各自根、叶契约；目录树、叶的 Parent 和父根登记表共同构成清单。

## 生命周期布局

```text
specs/
├── README.md                         编写规则与模板，不做逐条索引
├── implemented/                      已采纳并生效
│   ├── <domain>.spec.md               系统根契约
│   ├── inner/<area>-<name>.spec.md     业务、协议与实现叶契约
│   ├── architecture/yyyy-mm-dd-*.md   结构性决策记录
│   └── process/yyyy-mm-dd-*.md        工作流、工具与规范治理决策
├── proposed/                         未采纳提案；根提案在顶层
│   └── inner/                        叶契约提案
├── rejected/                         已否决记录，仅保留护栏
├── archived/                         已失效记录，仅保留历史
└── tools/                            只读静态检查入口
```

- **L1 状态唯一**：每条记录恰好位于一个生命周期目录，header 状态与目录一致。
  rejected、archived 保留原相对层级；不得把片段伪装成独立历史记录。
- **L2 按需创建**：不预建空目录、不放占位文件；首条记录与目录在同一改动中创建。
- **L3 规范与交付分离**：implemented 表示要求或决策已经采纳并生效，不表示代码
  已实现、构建通过或能力已验收。proposed 表示尚未采纳，即使已有部分代码。
  未采纳能力的详细设计留在 proposed，生效契约仅保留一行提案指针。
- **L4 过程归属**：方案、阶段进度、实现缺口、命令输出、测试数量及验收证据归
  `doc/<workspace>/iteration/` 或对应迁移台账；契约可引用入口，不复制进度账本。
- **L5 状态转换**：提案经明确采纳后整体进入 implemented，同步父根登记及引用；
  明确否决后进入 rejected 并说明理由；生效契约整体失效后进入 archived，指向
  后继或失效决策。未验收不是采纳、否决或归档依据，禁止自行推断采纳。
- **L6 实现漂移**：正确的生效要求约束实现，不迁就错误实现；要求被明确修订时
  先改契约，再同步实现。不得把尚未获得证据的交付写成已完成事实。

## 根契约与叶契约层级

- **H1 根契约**：拥有稳定领域、不变量、边界与子契约映射。implemented 根集合
  最多十个物理文件，每份最多 400 行；叶和决策不计入根预算。
- **H2 叶契约**：拥有聚焦行为或机制，可约束多个实现仓库。schema、API、状态机、
  参数、实现归属与仓库工作流细节放在 inner，不因实现仓库数量上升为根。
- **H3 唯一身份**：implemented 与 proposed 的 Contract-ID 全局唯一。
  根 ID 为一个 kebab-case 段，叶 ID 为 `<root-id>/<leaf-id>`，移动目录不改变身份。
  rejected、archived 可保留历史 ID，但不与生效文件竞争权威。
- **H4 父子闭合**：Parent 精确指向本注册表根文件，根 ID 与叶 ID 前缀一致。
  生效叶只能依附生效根；提案叶可依附生效根或提案根。父根的 Inner contracts
  必须且只能登记归属自己的、与父根状态相同的叶，每项提供一行职责。
  未采纳叶依附生效根时不进入生效根登记表。
- **H5 唯一归属**：同一规则、参数默认值、schema 和词汇表只有一个可编辑权威。
  其他契约引用路径及条款，不复制定义；规范只放 specs，不建项目本地副本。

## 命名与 header 规范

- **F1 路径**：契约仅允许生命周期顶层的 `<domain>.spec.md` 和
  `inner/<area>-<name>.spec.md`，不增加项目 spec 子树。决策仅允许
  architecture、process 下的 `yyyy-mm-dd-topic.md`。
- **F2 公共头**：第 1 行中文标题，第 2 行空行，第 3 行 Status。
  implemented 使用 `Status: implemented`；其他状态使用 `Status: <状态> — <中文理由>`。
  除替代关系的多条路径外，不允许同一 header 字段重复。
- **F3 契约头**：第 4 行 Contract-ID；叶的第 5 行 Parent，根不声明 Parent。
  字段间不插空行。模板中的 `<...>` 只用于说明，实际记录不得留占位符。
- **F4 决策头**：Status 后依次为 `Date: yyyy-mm-dd`、
  `Record-Format: structured | historical`；日期与文件名一致。
  每条替代关系单独一行 `Supersedes: specs/...` 或 `Superseded-by: specs/...`。
- **F5 语言与隐私**：说明文字使用简体中文；代码标识符、协议字面值、路径、URL 和
  header 字段保留原样。不写主机凭据、个人用户名或机器特定路径；可写公开服务标识及角色名。

## 正文模板

> 下列标题与顺序是必需结构。章节必须有具体内容，不放空表或通用占位段落。
> 可保留原有数字节号作为下级标题；重排不得静默改变条款含义或定位。

### 根契约模板

```markdown
# 中文领域契约

Status: proposed — 待评审
Contract-ID: <root-id>

## 范围
说明领域、约束对象和系统职责。

## 不变量
列出稳定系统要求，不放具体接口和参数表。

## Inner contracts
使用“契约路径”和“职责”两列表格登记同状态叶契约。
没有叶时说明根自身完整约束的具体边界，不放空表或占位叶。

## 边界
说明不拥有的领域及其真实 owner。
```

### 叶契约模板

```markdown
# 中文机制契约

Status: proposed — 待评审
Contract-ID: <root-id>/<leaf-id>
Parent: specs/implemented/<root>.spec.md

## 范围与非目标
说明约束对象、适用条件和排除范围。

## 术语与身份
说明领域术语与身份，外部词汇引用其唯一契约。

## 输入、输出与配置
定义或引用类型、单位、必填性、默认值、范围和非法输入处理。

## 行为规则
通过稳定条款定位定义触发条件、必须行为与可观测结果。

## 失败、取消与资源生命周期
定义失败、超时、取消、恢复、所有权和释放边界。

## 归属与依赖
说明唯一 owner、依赖方向、关联契约及提案边界。

## 条款检查判据
将条款定位与可判断的证据对应，检查结果保存在实施记录。
```

确实不涉及某类内容时，在对应章节说明具体原因和边界，不能只写“不适用”。
可增设下级章节，不为填写模板而新增接口、配置、状态或资源。

### 新决策记录模板

```markdown
# 中文决策标题

Status: implemented
Date: yyyy-mm-dd
Record-Format: structured

## 背景
记录作出决策时的事实与问题。

## 决策
记录被采纳的选择及适用范围。

## 理由与放弃的选项
说明依据及未采用方案的取舍。

## 影响
说明受影响的职责、契约、调用方和限制。

## 关联契约与替代关系
引用契约、实施记录；替代关系与 header 的精确路径一致。
```

- **D1 冻结**：决策保存当时事实，不作为当前接口或验收结论的权威。
  修订另建记录，两端用 Supersedes / Superseded-by 双向关联；部分替代在新正文明确范围。
- **D2 导航维护**：允许修复坏链接、补 header 和双向关系，不改写当时方案、证据或结论。
  实体简称可按仓库命名规则归一，但必须保留当时所指实体，并在实施记录列出文字映射；
  代码标识符、路径与历史引用原文不得借此改写。
  规范整理移出误入的后续状态时，由新记录说明处置，不静默改写历史。
- **D3 历史例外**：2026-10-14 之前已有决策标记 Record-Format: historical，
  保留原正文结构，免于新模板重排。例外仅针对冻结历史，新记录不得使用。

## 条款写法与引用

- **W1 可判定**：强制要求用“必须”“不得”，允许项用“可以”，建议项用“建议”。
  一条要求说明对象、触发条件、行为和可观测结果，涉及失败时说明处置。
  不得仅用“合理处理”“及时完成”等无判据措辞。
- **W2 稳定定位**：使用文件内编号，如 R1、B1 或原有数字节号加命名条目；
  引用使用 Contract-ID 加条款定位，表格使用字段名或接口名定位。
  原有 G/R/B/S/X 编号保留，新增要求不得复用退休编号，不设跨全部契约的中央流水号。
- **W3 完整边界**：接口和配置明确类型、单位、可选性、默认值、范围及异常处理；
  完成条件指明判定者、依据与失败条件；资源说明获取、释放、取消和迟到事件归属。
- **W4 当前要求**：生效要求写契约，未采纳设计写 proposed，理由写决策，进度与证据写 doc。
  退役要求仅留必要禁令或一行后继指针，不写迁移过程叙述。
- **W5 引用闭合**：本地 Markdown 链接、Parent、根登记和替代关系必须指向真实文件。
  反引号中的源码路径可能属于外部 owner，结构检查不将其当作实现存在性证明。

## Agent 执行约束

> 以下义务约束后续 agent 的契约文档工作；根 `AGENTS.md` 是读取入口，客户端规则只作引导。

- **A1 先读再改**：任务涉及契约新增、修订、移动、归档、登记或契约引用时，必须先完整
  读取本文件，再加载涉及领域的根、叶契约；不得只依据已有示例、搜索片段或历史方案修改。
- **A2 按类型落盘**：修改前必须确定唯一 owner、记录类型、生命周期和对应模板；
  修改时遵守本文件全部适用条款，同步受影响的父子登记、链接和替代关系。
- **A3 不得自行放宽**：不得为消除当前检查错误而擅自删除判据、放宽规范、伪造采纳或
  扩大历史例外；规则变更必须有使用者明确授权，先修改本入口并记录理由，再同步相关文件。
- **A4 检查与许可**：获当前任务的文档检查许可后，修改前、修改后必须执行本文件规定的
  结构门禁，并完成授权范围内的人工文档复核；修复发现的问题后重新检查。
  文档检查不得自动扩展为业务测试、构建、部署或业务内容审查，未获许可遵循 C3。
- **A5 交付如实**：交付必须说明检查范围、实际命令及结果、未覆盖项。门禁失败、
  检查未运行或复核未完成时，必须明确标记待检查或剩余问题，不得宣称已全部合规。

## 编写与变更流程

1. 分类并定位唯一 owner，确定根、叶、决策或过程材料。
2. 按模板形成提案；已有生效契约的修订理由先在实施方案形成，不复制同 ID 权威。
3. 审阅职责、接口、异常路径、完成条件和跨契约一致性，记录明确采纳依据。
4. 采纳、否决或整体失效时，同步状态、路径、父根登记、引用与替代关系。
5. 要求变更先落契约，再改实现；真实交付状态与证据在实施资料维护。
6. 提交前按许可运行结构检查和人工语义审阅，执行隐私检索；
   提交使用 `git commit --no-verify`，不安装或启用预提交钩子。

## 检查机制与许可边界

只读入口：`python3 specs/tools/station-host-spec-lint.py`，支持 `--repo-root <仓库根目录>`。
检查目录、命名、header、ID、父子登记、必需章节、本地 Markdown 文件链接、
替代关系及根预算。只读文件，不访问网络，不调用测试。

- **C1 结构结果**：结构错误输出到 stderr，退出码 1；未发现结构错误时退出码 0。
  运行故障返回非零，不用空结果冒充通过；拒绝符号链接及未知结构。
- **C2 人工审阅**：唯一归属、规则矛盾、条款充分性、中文表达、凭据和机器值、
  实现真实性、链接片段及历史正文未被改写仍须人工审阅。结构通过不代表这些事项通过。
- **C3 统一许可**：未获使用者明确许可，不运行测试、门禁或验证性验收，不读取测试资料。
  新增脚本不构成执行授权。执行结果及授权范围记录在实施方案，不写入本规则入口。
- **C4 其他引擎**：当前仅提供上述入口；其他旧门禁尚未迁移，不描述为本仓库已有能力。
