跟读：一次向前平移的完整旅程#

以 basic_flight.translate 为例，沿真实函数入口跟踪一次调用从批准到终态。下面是说明性情境，不是本次运行记录。

  1. 站端计划中有“向前平移 1 米”。create_batch 登记步骤和记录，approve_batch 放行此 call_id，_dispatch_step 开始当前步骤。
  2. publish_call 携带 direction、distance_m 和当前租约，经 RpcPlaneClient.execution 发给 lx/<stack>/rpc。
  3. RpcMethods._execution_call 按 method 查注册表；runtime 校验、占槽并记录 accepted。普通调用进入控制面队列，由 ToolIntake 交给 engine 的工作流入口。
  4. dispatcher 从 WAIT_FOR_MISSION 转到 DISPATCH，按 call.name 找到 TranslateSkill，调用 plan_tick。
  5. TranslateSkill 读取新鲜 odometry，以当时机体水平 yaw 将 forward/left 方向变换到 world，生成位置与 yaw 目标。不会把“前方”当成固定世界 x 轴。
  6. 共享宿主提交给 ActionSession；待执行资源新鲜、ready、stop_confirmed 且 action 连接成立，才发送 ExecuteWaypoints goal。
  7. 服务端检查坐标、点数、高度、yaw 策略与后端能力，然后 EGO 建立航点窗口，规划/重规划并向下游输出轨迹采样命令。
  8. L2 控制器消费 /setpoint_cmd，动力学更新并发布 odometry。planner 消费进度加上新鲜观测触发原目标停稳检查；成功候选还要经过保持接管与再次动态停稳。
  9. ActionServer 返回 SUCCEEDED；客户端事件泵按发送 token、启动标识和 owner/generation 归属接收结果。技能据结果作裁决，工具 runtime 只提交一次 done。
  10. RpcMethods.on_event 把终态投到 rpc_outcome；L4 按 call_id 完成当前记录，再推进下一步骤或结束批次。

平移与旋转有各自的领域判据

平移按新鲜状态中的 yaw 计算 world 位移，目标保留当前高度与朝向。旋转先检查部署预算，再按每段不超过 90° 分段；等待期间对相邻 yaw 做 atan2(sin Δ, cos Δ) 解缠，累计实际转角。时间倒退、观测间断、缺 yaw_rate 或采样不足以分辨旋向时失败；每段成功结果还要与累计期望角核对。

FlightSession 在地面高度配置存在且当前地面状态合格时记录候选位置；后续观测达到 airborne_height 才转为有效原点。回到地面附近并低速时清除原点；frame 改变、源时戳倒退、显式 reset 也使会话失效。return 读取有效原点的水平位置，目标高度直接取当前 state.z，最终仍受执行高度边界约束。它既不是回到上一任务点，也不自动降落。

取消与急停：任务释放和物理停稳分开#

取消优先使旧调用失效，再请求执行端保持。任务引用可立即释放，设备停止确认仍需要继续推进。

  1. 站端 cancel_batch 先将批次标为 cancelled，并把 entry / running 的未结束记录补成本地取消结果；随后发独立的 basic_flight.emergency_stop 调用。这个本地账本收尾不证明设备已经停下。
  2. L3 runtime 对同源新调用可以抢占旧调用，旧调用提交唯一 fail；取消与急停先经中断口调用 ActionSession.request_stop，再由优先消费者清理 engine 工作流。
  3. ActionSession 设置 blocked，丢弃 pending、结果缓存与 active 任务引用，保存不含技能 owner 的 StopRecord；独立尝试全局 emergency_stop 和具体 goal handle cancel。两个出口分别尝试，某个失败不跳过另一个。
  4. 服务端 CommandOutput 增加输出代次并置 blocked，阻断旧规划计算或迟到 cmd 的发送权。保持命令以当前有效位姿为参考，速度、加速度、jerk 和 yaw_dot 清零，并通过独立节拍输出。
  5. WaypointExecution 持续检查后端保持接管与动态停稳；确认后才能释放执行资源。停止超时会留下 fault / stop_confirmed=false。
  6. 客户端要收到停止请求之后的新鲜 ready 快照，并满足 boot / recovery_generation 的确认关系，才解除 blocked。单纯重新建立网络连接不能解除物理资源闭锁。
